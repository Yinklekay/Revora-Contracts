## Summary

RevoraContracts dispute-hardening PR: prevent low-share holder griefing and remove the issuer-next-to-frozen-offering from being the single point of truth for lifting a Critical freeze.

- Holders can still open on-chain disputes and attach off-chain evidence via `open_dispute`, but `open_dispute` now accepts `Standard` severity only. Reaching `Critical` requires an explicit `escalate_dispute` call by the contract admin.
- `resolve_dispute` authorization is now split by severity: the contract admin can resolve any dispute, while the offering issuer can resolve only non-Critical disputes. An issuer under a Critical dispute can no longer unilaterally clear the freeze.
- Critical freezes are now time-bounded: a per-offering `CriticalFreezeWindowSecs` (default `DEFAULT_DISPUTE_WINDOW_SECS`, configurable via `set_critical_dispute_window`) bounds how long a holder-opened critical freeze can remain active before auto-expiring. The window is measured from `opened_at`, and `is_dispute_freeze_active` returns `false` once the window elapses unless admin renews/escalates.
- Standard disputes and issuer-initiated disputes keep their existing behavior, with full doc comments, new public entrypoints/query methods, new storage keys, and a new audit event.

Closes #1328

## Why this PR exists

### Previous entrypoint behavior

| Entrypoint | Prior authorization | Prior freeze effect |
|---|---|---|
| `open_dispute` | `holder.require_auth()` + `share > 0` | `Critical` severity immediately incremented `CriticalDisputeCount` and could freeze claims for the offering. |
| `resolve_dispute` | `caller == dispute.offering_id.issuer` | Only the disputed issuer could resolve any open dispute, including Critical ones. |
| `is_dispute_freeze_active` | read-only | Returned `true` whenever `CriticalDisputeCount > 0`, with no expiry or renewal guard. |

### Why that was dangerous

- `open_dispute` previously required only `holder.require_auth()` and `share > 0`, and directly incremented `CriticalDisputeCount` when `severity == Critical`. Any dust holder could freeze an entire offering indefinitely.
- `resolve_dispute` previously enforced `caller == dispute.offering_id.issuer`, so the disputed issuer was the only party able to lift the freeze — a direct conflict of interest with no admin override.
- `is_dispute_freeze_active` only checked `CriticalDisputeCount > 0`; there was no expiry, bond, or renewal guard.
- `MAX_OPEN_DISPUTES_PER_HOLDER` (5) was a per-holder cap, not per-offering, so it did not mitigate an offering-wide freeze.

## What changed

### Contract (`src/lib.rs`)

- `open_dispute` now rejects `DisputeSeverity::Critical` with `RevoraError::CriticalDisputeRequiresEscalation`. Standard disputes behave as before.
- New `escalate_dispute(env, caller, dispute_id)` — admin-only. Re-reads the dispute, confirms it is `Open` and `Standard`, promotes severity to `Critical`, increments `CriticalDisputeCount` (with the existing freeze-on event semantics), and emits `EVENT_DISPUTE_ESCALATED`.
- New `resolve_dispute` authorization split:
  - If `dispute.severity == Critical`, only admin may resolve (caller must equal current admin). Issuer resolution returns `RevoraError::IssuerCannotResolveCritical`.
  - If `dispute.severity == Standard`, either the offering issuer or the admin may resolve.
- New `is_dispute_freeze_active(env, offering_id)` now returns `false` when no period has been closed **or** when the oldest still-open critical dispute (by `opened_at`) has exceeded `CriticalFreezeWindowSecs(offering_id)`.
- New `get_critical_dispute_window(env, issuer, namespace, token)` and `set_critical_dispute_window(env, caller, issuer, namespace, token, window_secs)` (issuer or admin; bounded; emits `EVENT_CRITICAL_DISPUTE_WINDOW_SET`).
- New storage key `DataKey3::CriticalDisputeWindowSecs(OfferingId)` (default `DEFAULT_DISPUTE_WINDOW_SECS`).
- New event `EVENT_DISPUTE_ESCALATED` (`sym_dsp_esc`).
- New error variants on `RevoraError`: `CriticalDisputeRequiresEscalation`, `IssuerCannotResolveCritical`, `CriticalDisputeWindowExpired`.
- Added doc comments for all new/modified entrypoints describing auth, errors, and events.

### Client / test helpers (`src/test_dispute.rs`, new `src/test_dispute_freeze_window.rs`)

- Extended `RevoraRevenueShareClient` usage in tests for new entrypoints (via existing `try_*` wrappers generated by `#[contractimpl]`).
- New test suite covering:
  - Holder-opened critical dispute without admin escalation does **not** block claim.
  - Admin-escalated critical dispute blocks claim; admin resolution lifts it.
  - Issuer **cannot** resolve a critical dispute; issuer can still resolve Standard disputes.
  - Freeze auto-expires after the configured window unless renewed by admin escalation.
  - Admin can configure/override the critical freeze window; unauthorized / out-of-range values are rejected.
  - Standard dispute behavior is unchanged (no freeze, issuer/admin may resolve).

### Storage layout (`tools/storage_layout_schema.rs`, `docs/STORAGE_LAYOUT.json`)

- Added `DataKey3::CriticalDisputeWindowSecs(OfferingId)` entry (u64, offering-scoped).
- Updated schema + JSON to include the new key and events for auditability.

## Security notes

- Fail-safe default: newly opened critical disputes do **not** freeze claims unless confirmed by admin. This protects holder liveness against griefing while preserving a governed escalation path for genuine disputes.
- Conflict of interest removed: the disputed issuer cannot unilaterally clear a critical freeze. Admin resolution is the only path for critical disputes; issuer retains resolution rights for Standard disputes.
- Time-bound freeze: even an escalated freeze expires after `CriticalFreezeWindowSecs`, preventing indefinite freezes from a single escalation. Renewal requires another admin action.
- Auditability: escalation and window-configuration events are emitted so indexers/analysts can trace who escalated, when, and under which window.

## Out of scope

- `resolve_dispute` status/counter bugs (tracked separately).
- Formatting-only changes, snapshot-only tests, disabling checks/type errors, unrelated refactors.

## Notes for reviewers

- The freeze-window check uses `opened_at` of the oldest still-open critical dispute for the offering. This is a simple, deterministic bound that does not depend on period close timing for holder-opened disputes.
- If an offering has no closed period and no admin escalation, `is_dispute_freeze_active` is `false` — consistent with the existing “no deadline, no freeze” posture for dispute-window checks.
- If you want the safety role to be distinct from admin, the escalation entrypoint already uses `require_admin`; we can parameterize the role later without changing the security model.
